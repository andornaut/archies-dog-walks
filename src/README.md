# Tech Plan

## Platform and delivery

- **Deploys:** see [Deploying](../README.md#deploying).
- **Engine:** Phaser 4 and TypeScript, built with Vite into static files.
- **Hosting:** Cloudflare Workers static assets, with a Worker (`src/pwa/originWorker.ts`, built into `dist/.worker/` by `src/tools/originWorkerPlugin.ts`) that runs only where no file matches and serves the archive-only game files from the deployed build's group archives, through the kit's `createGroupArchiveMemberReader`, with their HTTP headers, ETag and byte ranges.
- **Platforms:** the web, including phone browsers and installed web-app windows.
- **Repo:** GitHub repository `andornaut/archies-dog-walks`.
- **Tooling:** follows `andornaut/cloudflare-starter`: Vitest, ESLint with the shared house rules, Prettier, markdownlint and Dependabot. The Node version, the npm commands and CI are in the [root README](../README.md#developing).

## Site

The pages and `public/` are laid out in the [root README](../README.md#developing). `pages/` is Vite's root, its HTML pages the build inputs, and they load modules as `/src/...`, which `vite.config.ts` aliases to the repository's `src/`. The game installs the versioned `@andornaut/game-kit` release pinned by URL and integrity in `package-lock.json`. Node, TypeScript, Vite and Vitest resolve its compiled JavaScript and declaration exports through native package resolution. `SOURCE_COMMIT` in the installed package records the canonical source revision. `vite.config.ts` imports `gameViteConfig` from the kit's `build/gameConfig`; it loads `src/tools/viteConfigModules.ts` through Vite’s module runner. Vitest transforms the installed package so game tests can mock Phaser at the package boundary; test discovery remains limited to `src/**/*.test.ts`.

## Architecture

The player-facing rules (controls, layout, movers, pulls, feedback) are in `docs/design/gameplay/design.md`; this section covers how the code carries them out.

The [planner work record](../docs/planner-work.md) summarises the spawn planner's contract and qualification results.

### Data-driven entities

- **Boundary:** code implements mechanisms; data selects which mechanisms an entity uses and supplies its profiles, traits and tuning values. Adding an entity that uses existing mechanisms should require data and assets, without a new runtime branch on its id. Dispatch on a validated mechanism kind belongs in code.
- **Current model:** `src/data/types.ts` defines the movement union; obstacle and encounter records select movement and shape, and `world.ts` supplies neighbourhood weights. `runner/moverSpecs.ts`, `runner/moverPlanning.ts` and `runner/movers.ts` interpret these records into seeded paths and evaluate them. Pull eligibility reads the encounter resolution. Some presentation policies still select entities by id; new profiles should make those assignments explicit without changing their behaviour.
- **Representation:** use typed literal TypeScript records or validated JSON. Keep entity assignments, reusable profile parameters, capabilities, effect assignments and adjustable values declarative. Use closed profile kinds and check references, ranges and compatible combinations; reject unsupported kinds rather than silently selecting a default.
- **Sharing:** put game-independent pure mechanisms and validation utilities in the shared game-kit source. Keep each game's entity ids, schemas, profile assignments, content and balance data local. Share a mechanism when both games use the same semantics, with game-specific inputs supplied explicitly.
- **Verification:** preserve seeded random streams, draw order and replay behaviour when moving policy into data. Test profile validation and mechanism behaviour, compare representative session fingerprints, and regenerate shared exports when their inputs change. Behaviour changes also update the corresponding [gameplay rules](../docs/design/gameplay/README.md). A data-only refactor preserves existing outcomes.

### The walk

- **Collisions:** the pack uses fixed logical contact silhouettes for the walker and dogs, with hit rectangles `PART_INSET` inside them and a pickup outline using the same fixed geometry (`src/layout/packFormation.ts`). Rendering anchors and animation pixel bounds are measured separately; cosmetic art changes do not resize contacts, formation or planner geometry. An obstacle's hit box is the bounding box of its sprites' opaque pixels at its depth, `PART_INSET` inside, cut to its lanes (`obstacleHitBox` in `src/runner/walk.ts`). A standing obstacle's hit box runs up the road no farther than its footprint's rows, `cell.length` each (`hitReach`), so standing art drawn taller than its rows draws over the road behind it but hits only within them; a moving one hits as tall as it is drawn. Pickups and lucky finds use `ROAD_HIT_SIZE` (`src/assets/spriteKeys.ts`). The spawn planner spaces rows by the longest obstacle as it hits (`plannedCellInset` in `src/runner/walk.ts`), so taller standing art never spaces them wider, and measures the pack-fit gap as drawn: each kind at its own hit length (`itemHeight`) and the pack at the tallest pack's hit boxes, its outline (`tallestPackLength` in `src/layout/packFormation.ts`) less `PART_INSET` at each end.
- **Cosmetic layers:** ambient movers (`src/road/ambient.ts`, each zone's mix in `src/data/ambient.ts`), distraction movers (`src/road/distractions.ts`), roadside props (`src/road/roadsideProps.ts`) and hit obstacles left on the road as scenery (`src/road/struckScenery.ts`), and darts that stop on the verge, kept as scenery once the walk drops them off the road (`src/road/vergeScenery.ts`), collide with nothing and the walk never reads them. Ambient movers draw from the run's `ambient` stream and distraction movers from its `distractions` stream, which the session never reads, and roadside props draw no random numbers, so a seed plays the same walk with or without them. Red herring crossers (`src/road/herrings.ts`, from the zone plan's `Road.herrings`, see Movers) draw nothing on the road: `ItemViews` draws each as its mover, in its art at its depth with no cue, from as its row comes on screen until it has crossed, and none with reduced motion. Distraction movers are red herrings: `counts.distractionsPerZone` per zone, one in each equal stretch of it, each gone before its row is down to `multipliers.distractionEndRoadShare` of the road ahead of the pack. They wear the zone's own hazards (`distractionKinds`): its one-lane `onFoot` minor obstacles weighted above 0, by those weights, each only with a walk, hop or run tag; a zone with none takes the ambient walkers. Each takes one of three patterns at `probability.distractionPatternOdds`: it steps from the verge into the edge lane, stands there for `multipliers.distractionVisitLingerShare` of its time on screen and steps back off (visit), waits at the road's edge half on the verge (where a dart waits idle) then leaves (edge), or starts in the edge lane as its row comes into view and stands there for at least `multipliers.distractionLeaveLingerShare` of its time then steps off (leave). A visit walks back off the road no faster than it stepped on, and a test on the shipped tuning holds the linger to that. It shows no move cue: the view draws its body sprite only. None is drawn over a pickup or an obstacle, or stands on a roadside prop's footprint (its drawn width across, from half a cell nearer than its feet to a cell beyond): as its row comes into view, it checks the road's items, the zone's pending spawns and the verge scenery along their paths, and the props' footprints, over its whole time on screen, and tries the drawn side, then the other side. If both are blocked, it retries one cell farther along the same stretch until it passes the last safe row, then skips that distraction. The initial row leaves room for at least two retries when the stretch permits. They sort by row with the roadside props, so a nearer prop stands in front, under every road sprite.
- **Fixed step:** `RunScene` steps the walk session at 1/60 s, as many steps per frame as the wall-clock time since the last frame holds, banking at most a second (`@andornaut/game-kit/runtime/clock/fixedStep`). It reads the frame timestamps, not Phaser's delta, which Phaser smooths and clamps, so a slow device keeps to real time and a replay matches the run step for step.
- **Gear drops:** after its lucky finds, `auxiliarySpawnQuotas` (`src/runner/zonePlan.ts`) draws a zone's gear drops from `zone-<zone>-gearDrops` (`drawGearDrops` in `src/rules/gearDrops.ts`): `counts.gearDropsPerZone` for the walk position, rounded by `chanceRound` (`@andornaut/game-kit/runtime/random`: the whole part, and one more at the fractional part's chance), each item drawn by 1 over its price among the items not in effect (the Pocket's and the found one) and not drawn before it in the zone. A drop's road kind is its gear id (`isGearDrop`), a one-cell quota that blocks no lane, placed like a standing lucky find and drawn as `drop-<gear>`. Touching one grabs it as a lucky find is grabbed, with no hit and no Long reach. The walk holds one found item at a time (`RunState.foundGear`) beside the Pocket's: `grabGear` ends the found item's effects (every modifier, dodge, immunity and skip whose gear source is marked `found`, then the spare treats held cut to the room left (`holdSpareTreats`), then each owner's hearts held to their max), then applies the new item's with a `found` gear source. Each effect acts where its rule reads it, so a found item works mid-walk as the Pocket's does: a maxHearts modifier raises maxes, not hearts. The found item takes the effect well after the Pocket's, and its strip line, popup, hold card and the names a breakdown gives it (`gearSourceName`, `runText.foundGear`) say it was found.
- **Lights:** `src/road/lights.ts` reads the light defs from `shared/lights.json`, which art writes: per key a `shape` (`"ellipse"` or `"band"`, centred on its anchor, or `"cone"`, its apex on its anchor, widening to `width` at `height` away, pointing down), a `width` and `height` in px at full size, a palette `colour`, and 1 to 3 `rings`, outermost first, each a `scale` of the shape (toward the apex for a cone) and a `strength`, each ring inside the last and brighter. `src/scenes/run/lightsView.ts` bakes each def once into a texture whose ring pixels hold their strength of the colour, and draws it with an additive blend over the road, the backdrop's approach and the shadows, under every sprite, scaled with its anchor's depth and faded in from the juncture like the props. A verge's `pools` place lights along its zone's road (`src/road/lightPlaces.ts`): each names a def by `light`, lies `across` from the road's centre line, and repeats `every` road px on both sides from `offset.left` and `offset.right`, counted from the zone's start strip as roadside props' slots are, so lights line up with props; an optional `zones` lists the zone ids it shows in. The table's `attach` lists, by sprite key, the lights every sprite of that key carries, whichever view draws it: drawn last each frame, `LightsView` finds every visible sprite of such a key in the scene, at its feet, scale and flip (`anchorSprite`), and places its lights (`placeAttachedLights`) just under it, at its opacity, cut off at the juncture as it is, while a band mover's stay whole. Every light is culled by its own drawn rect (its texture's at its scale and rotation), once wholly outside the walk view, never by its sprite's bounds or visibility: a roadside prop whose art has left the screen stands hidden as a light carrier (`placeRoadsideLights`), from behind the feet to the cross street, so its lights follow where it stands, while a light whose sprite ends, a mover leaving the road, ends with it. Each names a def by `light` and sits `dx` and `dy` px at full size from the sprite's feet as drawn (whole or half px), or, for a lamp that moves as the sprite animates, by `frames`: an offset for each frame of the sprite's sheet, in sheet order, `null` on a frame that shows no light. It may set a cone's `angle` (degrees as drawn: 0 right, 90 down, 180 left, so a sprite drawn facing the pack shines down at 90), a `pulse` (a strength for each frame of the sprite's sheet, a frame named for its place there, as in `cyclist@75 3.aseprite`), `facesRoad` and `zones`. A flipped sprite mirrors its lights' `dx` and `angle`. A roadside prop is never flipped: a light with `facesRoad` is set out as for a prop on the road's right and mirrored on its left, so a lamp's beam, set from its bulb down and to the left, shines toward the road from either side; any other prop light stays as set. A prop held on its resting frame (see Roadside props) holds its lights at that frame's strength. Validation throws on an unknown field, key, colour or zone, and tests check that each attached sprite exists, that a sheet of several frames has a `pulse` and `frames` entry for each, and that each cone's apex lies on its sprite's lamp, on every frame it shows on, at every depth step, on both sides: on or beside a lit pixel, a white one only where its run of white has a cream ring, as a rider's headlamp has and its chest band, helmet or reflector has not. Lights are drawing only: nothing in the walk, the rules or the simulator reads them.
- **Lucky finds:** each kind's count in a zone is `counts.luckyFindsPerZone` for the kind times the zone's `density.luckyFinds` (`zoneStats`), rounded by `chanceRound` from `zone-<zone>-luckyFinds`, in the table's order. The zone's finds are then shuffled (`zone-<zone>-luckyOrder`), and each is a quota of its own, a mover at the zone's mover share where its look moves (`zone-<zone>-luckyMovement`).
- **Spaced spawns:** a zone's lucky finds, and apart from them its gear drops, are spread so no two stand close: the ith of n takes every other one of 2n - 1 equal stretches of the zone (`spacedStretch` in `src/runner/stretches.ts`, held by `SpawnQuota.within`), so two stand in its first and last thirds. A standing one is placed only within its stretch, and a moving one starts in it or waits for a later row before the stretch ends, else stands still in it.
- **Movers:** `src/runner/moverPlanning.ts` compiles each mover's whole path from its frozen per-job motion streams, and `src/runner/movers.ts` moves it along that path, so a seed replays the same moves. A hopper's ways to hop grow as its hop shapes to the power of its count, so it takes at most `HOP_SEQUENCES_MOST` sequences of each count, drawn from the mover's `hops` stream where there are more (`hopSequences`, `src/runner/moverHops.ts`). Movement kinds keep their data names, the rulebook's archetypes mapping dash and swoop to `dart`, wander to `step`, stalk to `approach` and cruise to `inLane`. The pattern movers (`bounce`, `follow`, `stopAndGo`, `sway`) are steppers whose sequences `moverSpec` (`src/runner/moverSpecs.ts`) lays out with no draw: a bounce's and a sway's steps alternate a lane each way, a follower's are every sideways sequence of its count (2 to the power of it), and a stop-and-go's are pushes in its lane that each travel `factor - 1` of their length along the road. Each step after the first waits its kind's pause (`pauseSeconds`, or `stopSeconds`); a bounce, a follower and a stop-and-go cue every step, the pause stretched to at least the cue. Their count is drawn among their sequences' lengths (`drawnStepCount`, `src/runner/moverDraws.ts`). A `dive` is a dart that always stops in a lane, never turning back or stopping on the verge, crossing at `speed` of a dart's and sliding its last lane at `slide` of that (`isSliding`). A `merge` is a rider that, once its travel down the road is `mergeAt` of the way to the pack's rows (no sooner than its cue can show after it enters, and finishing before it reaches them), moves a lane to either side that stays on the road over `mergeSeconds`, after a cue (the wander mark); the planner places it as a rider over both lanes, one placement per side. A mover's body plays its `cue` tag, where its sprite has one, while its cue shows, a diver its `dive` tag while it slides, each once through, and a merging rider its `merge` tag while it moves across. Production `planZoneWithContext` routes placement through `slotPlanner.ts` and the unified native witness described under Spawn planning.
- **Pausing:** the walk steps only while `walkPaused` (`src/hud/topBar.ts`) finds nothing pausing it. Each overlay reports to `MenuFlow.pause()` (`src/scenes/run/menuFlow.ts`), so a new overlay pauses the walk too.
- **Pseudo-3D road:** game logic keeps a flat road (lane x, distance ahead of the walker in road pixels, scale 1 at the pack). Only drawing projects it, through `src/layout/projection.ts` with `ROAD_CAMERA` (`src/layout/screen.ts`). `src/road/roadDraw.ts` draws the road and verges row by row into one canvas texture, up to the backdrop's cross street: on the band's junction rows (`junctionRows`, between the near corners) it draws the road surface alone, and on its approach rows (`roadIntoBand`) the verge too wherever the backdrop shows the verge's ground, seams, dots or marks, so the backdrop's own still detail never shows beside the moving verge. A row covering several strip rows keeps the strip's lines along the road (runs of 8 or more rows down a column) wherever it covers them, and its seams across the road (runs of 8 or more columns, under 8 rows thick, such as paving joints) on exactly one run of rows per pass, so no seam blinks however far away it is. Road sprites scale smoothly with distance, drawn from the smallest of their art steps (1x and the manifest's variants at every 1/16 down to half size, `<key>@94` to `@50` in `shared/depth-steps.json`, that are loaded) at least their projected size (`src/layout/depthScale.ts`), shrunk by at most 1/16 of full size with linear filtering, so 1 px details fade rather than blink as they approach.
- **Pulls:** `src/runner/pulls.ts` draws no random numbers: each pull follows from the road, so the input log needs nothing for them. A darting squirrel is a target from its cue on, never while it waits idle at the road's edge (`isWaiting`); the scene and the simulator both take their pulls from `stepPulls`, so the one check covers both. A pull into a lane where a lane-blocking obstacle or mover would reach the pack before the player could steer back (`seconds.pullReactionWindow`) waits until the lane clears. A squirrel blocks no lane and its path may cross obstacles' cells, so this check at the moment of the pull, not the planner, keeps every pull fair.
- **Roadside props:** `src/road/roadsideProps.ts` places them from `shared/roadside.json`, per zone by art id, on a grid of slots `slot` road px apart along each side. Lawn props stand beyond the sidewalk, each side alternating lots and gaps. Curb props (a zone's optional `curb`: `groups` of props, and per side a `start` and `stride`) take a group at every slot and stand wholly inside the zone's curb band (`curbBand` in `src/road/roadside.ts`): the sidewalk, 2 road px in from each edge, paving counting as a sidewalk 44 px wide (`sidewalkTo`); a verge with no sidewalk has no band. Verge movers stop 32 road px past the sidewalk (`vergeStop` in `src/road/ambient.ts`), so a stopped mover's frame stays clear of the band; sidewalk walkers pass in front of curb props. No prop stands on a zone's start strip. Lawn and curb props share one pool of `ROADSIDE_LIMIT` sprites, drawn through the projection from their depth steps like road sprites. Props stand up to the cross street (the stage's `reach`, the junction's top row), past the road's far edge, and fade in with their shadows from there to the far edge (`fadeIn` in `src/road/roadClip.ts`); movers and items come into view at the far edge, opaque. A road sprite standing on the road draws whole, its top over the backdrop band; one standing past the cross street shows nothing above it. A prop whose sprite has an `idle` tag of two or more frames loops it, each frame shown for its own duration from the sheet, on the walk's ambient clock, which holds while the walk is paused or a firing holds it; a one-frame tag, or none, draws still. Each placed prop starts its loop at its own phase, a share of the loop's length hashed from its road distance from the walk's start and its signed across (`roadsidePhase`), so props of one kind never change in step and a prop keeps its phase as it scrolls. Every depth step shows the same frame, so each step's sheet carries the same frames and durations under the tag. With reduced motion a prop holds the tag's first frame, so that frame is its resting look.
- **Spare treats:** a `spareTreats` modifier, such as the Fanny pack's, sets how many spare treats the pack holds (`spareTreatRoom` in `src/rules/spareTreats.ts`), counted in `RunState.spareTreats`. A treat grabbed while every walking owner is at their max is held when there is room (`storeSpareTreat`), and otherwise pays `money.treatCash` (`grabTreat` in `src/rules/treats.ts`): a money change whose base cause is the treat, carried cash like a tip's, but never a tip, so no tip modifier, tip label or tip tally touches it. The walk step reports it as its treat's `cash`, and the scene and the simulator both take it from the walk session. After changes made at once (a step's bumps in `stepWalk`, or the effects of a card, a fork, a contact or a lucky find in `outcomeOf`), `spendSpareTreat` gives `hearts.treat` back to the owner they lowered who is left with the fewest hearts, ties to the front dog, before `fireOwnersAtZero`. A loss Second chance forgave whole lowers no meter, so it spends none. The walk step and the outcome report it as `spareTreat`, and the scene and the simulator both take it from the walk session.
- **Verges:** `src/road/roadside.ts` reads each zone's verge from `shared/verges.json`, by art id: outward from the road's edge, the curb to `curbTo`, the strips, then the sidewalk or paving to `walkTo` (null: paved to the screen's edges) and the lawn. Every place across is in road px from the road's centre line (the road's edge is 160), and every length along in road px of walk distance, so seams, dots and marks scroll with the road. A verge's optional `pools` are lights repeating along it (see Lights).
- **Walk session:** `src/runner/session.ts` is the walk's one step order, pure and shared by `RunScene` and the simulator. A step applies its inputs (lane moves, heading home), then the pulls, the Zoomies' drift and the walk, then any firing hold; then it opens the queued cards, ends the zone (fees, then the fork) or plans the next zone. Its random streams are named from the run's seed (`runStreams`, see Random streams), so a seed and an input log replay the same walk wherever they are played. `resumeSession` goes on from a session saved between zones or at the walk's start (`unplannedStart`, `forkPoint`, `zoneStartPoint`): the fork it waited at opens, or the zone it was about to walk is planned. It returns events that the scene plays as sounds and effects and the simulator counts. A fork's choice or a neighbourhood cheat can defer the plan (`ZonePlanning`), leaving the session awaiting it (`awaitsZonePlan`); `RunScene` then plans it in a module worker (`src/runner/dom/pageZonePlanner.ts`, `src/runner/dom/zonePlanWorker.ts`) from the seed and the walk, with `planZoneFromSeed` as the step does, and holds the walk until `withZonePlan` takes the plan. The latest request wins; without a worker, or once it fails to load, the page plans the zone itself. A cheat pressed while a plan is still to come plans it on the page first. A walk's first zone, and a resumed walk's, are planned as the scene starts.

### Spawn planning

`planZoneWithContext` builds original configured role budgets through `planSlotSpawns` (`src/runner/slotPlanner.ts`). `world.ts` configures encounter-pool and minor-pool roles, each fixed or moving, by walk position. Modifiers scale the total once; largest remainders apportion integer roles in encounter-fixed, encounter-moving, minor-fixed, minor-moving order. `zoneSlotGuarantees` derives one guarantee for each positive-weight kind, in reservation order: moving roles before fixed roles, then larger footprint area, then more lanes, then kind name; `planZoneWithContext` checks they name exactly the catalogue's positive-weight kinds.

- **Commitment:** `slotCandidateDomains.ts` retains immutable native candidates and repeated movement variants. One `slotConstraintState.ts` transaction owns native geometry, cell ownership, conflict owners and checkpoint restoration. Runtime solves the original actual hazard and auxiliary requests together, preferring 100% delivery. Declared source weights guide seeded value order without removing available full profiles. Within one search frame, whose earlier placements stay fixed, runtime search moves a row behind the job's untried rows once two of the job's values there have been rejected for occupied cells or bodies (`SLOT_ROW_PRESSURE`, `src/runner/slotDelivery.ts`). Job order, the seeded kind order and every domain value are unchanged. Quiet coverage, the path, open lanes, screen caps and reaction gaps remain native constraints. A fresh `auditSlotPlan` checks exact role totals, guarantees, auxiliary identities and authored profile bindings, then invokes uncached `auditSpawnPlan` for geometry and global safety. Every emitted layout must pass its independent audit; exact and partial results use separate admission contracts.
- **Capacity:** authored capacity ceilings remain configuration limits, including after modifiers: a count above its ceiling is a configuration failure. No planner path constructs or audits the maximum composition. Complete runtime results retain `activeAudit`; partial results carry a separate partial audit.
- **Delivery:** `planSlotSpawns` is the only planner entry point and always applies the 90% delivery policy. `SlotPlanningContext` carries only the seed, zone index and work limits; it has no policy or search switches. Each neighbourhood independently requires `10 * delivered >= 9 * originalConfigured`, where the original denominator includes all active role and auxiliary logical requests. Optional requests, including rewards, may be omitted; all explicit guaranteed owners, authored kind and role minima, full movement capabilities and native safety and quiet-coverage rules remain required. Exact results keep `complete` status; certified partial results have distinct `partial` status and a separate partial audit that checks the original denominator, protected owners, profile bindings, identity partition and every native geometry and global rule. Delivery evidence retains original and delivered total and category counts, plus each omitted original key, role, auxiliary reference when applicable, known kind only when established, and a reason distinguishing an exhausted domain from a request not selected within the allowance. Materialisation preserves original job and profile identities and native insertion indices. Omitted, downgraded or substituted requests receive no delivery credit. Unfinished and unvisited search prefixes are not certified layouts
- **Failures and limits:** malformed definitions, unavailable pools/guarantees and counts above ceilings are configuration failures. Explicit anchor, candidate, template and slot limits bound construction. Propagation work has its own reported `propagationChecks` counter, bounded by the same numeric `candidateChecks` limit. Omission choices and incumbent certification share that unchanged allowance and must be explored before exhaustion; no second full-budget fallback is allowed. A search frame offers its optional request's omission only after a threshold of failed placement attempts, or when its domain is exhausted, so early failures do not spend the omission allowance before the request's domain is explored. Each runtime attempt explores with `SLOT_OMISSION_ATTEMPTS.explore` (`src/runner/slotDelivery.ts`). If it holds no certified floor-meeting layout once either work counter has used `SLOT_OMISSION_RESERVE` of the attempt's remaining allowance, the search restarts from the empty layout with `SLOT_OMISSION_ATTEMPTS.reserve` for the rest of that attempt; [`docs/planner-work.md`](../docs/planner-work.md) holds the values and budgets. The restart shares the attempt's counters and caps and is not a further attempt; exact searches never restart. Exhaustion without a certified admissible layout reports unsupported construction without claiming geometric impossibility. A failed independent certificate is an invariant failure. Continue optimisation toward 100% within the same bound.
- **Randomness and observation:** the planner's streams, one per purpose (see Random streams), derive the path, layout, full motion, weighted value order, auxiliary rewards and final skins from the session seed. Optional `observeSpawns` receives the actual `plan`/`planned` and `slots` evidence labelled `purpose: "runtime-actual"`, with its input, independent audit, assignments, delivery evidence and work counters. `ZoneSlotInput` captures the actual run, resolved budgets, authored capacity ceilings, geometry, tuning, profile definitions and frozen auxiliary requests. `replayZoneSlots` reconstructs the actual request from its JSON representation without auxiliary redraws. A zone without a certified layout returns a failed `ZonePlanOutcome` before the success observer, with its reason, input and, when the planner found none, its explicit failure evidence; the session stops the walk with it as a `ZonePlanningError`. Null encodes an unlimited quiet-row bound. This evidence is ephemeral and adds no resume fields. Input logs require the current replay version.

### Screens and UI

- **Accessibility:** reduced motion (a setting, defaulting to `prefers-reduced-motion`) drops decorative motion but keeps every highlight and state change, the road scroll and the lane slide. No state relies on colour alone. Press areas follow the [Art target geometry and compact HUD exceptions](../art/layout.md#controlstargets) (`MIN_PRESS` in `src/data/layout.ts`, the kit's `HIT_RULE.minTarget`). Text meets 4.5:1 contrast and essential icons 3:1.
- **Badge cards:** the Logbook's Badges tab and the end screen open one card for a badge (`src/home/badgeCardView.ts` and `src/hud/dom/badgeCard.ts`: the badge at 2x with its name, status, goal and line, over the whole game frame dimmed, the top bar included; a locked badge's status, Locked, in `GREYED.shortPrice`, the dark red of a shop price the bank does not cover), so a badge reads alike on both. The end screen's earned badges have no tap action of their own, so a tap and a press and hold on one both open its card: the hold opens it as the hold time passes, with `TILE_SLOP_PX`, and its release taps nothing. The strip holds 7 badges to a row (`BADGE_STRIP` in `src/home/badgesView.ts`); past 7 it takes two rows, split as evenly as they go (8 as 4+4, 9 as 5+4), each slot the fuller row's share of the width and each row centred, as a celebration's does too. The end screen's two-row strip grows 8px up into the panel's room, its bottom kept over Back to title (`endBadgeStrip` in `src/home/endLayout.ts`). The badges' second row comes before the owners' second lines (`grantedQuipLines`), and stays one row only where the panel with every closing line on one line would not end above two (`endBadgeRows`): 6 breakdown lines and 3 owners' rows, which takes a Start cash line, a dev start's. Shared movement evaluation uses `@andornaut/game-kit/runtime/motion`: `progressAt` clamps a segment fraction, `easeProgress` applies linear or sine-in-out easing, and `segmentAt` returns an immutable segment's position. Archie supplies cumulative road scroll as progress. Named movement profiles, seeded planning, cues, lane reservations, collision footprints and route admission remain game-owned; the shared evaluator draws no randomness and advances no clock.

Named signature recipes live in `src/data/movementProfiles.ts`. `MOVEMENT_ASSIGNMENTS` selects a leaf movement directly or through an explicit default and typed neighbourhood overrides; selectors cannot nest. Profile durations and follower delays are seconds; lane and row extents use grid units. `downFactor` is the total down-road velocity ratio. `finishAheadSeconds` guarantees minimum time before pack contact after all defining phases and delayed followers finish. The clearance uses the configured tail velocity and retains at least the same base-road-scroll visibility margin. Leg durations contain motion time only. The initial seeded start delay and cue form one stationary prelude; later cues add no turn pauses. Trail delays and animation phases use active walking time, excluding this shared entry hold, so all components remain separately staged and resume continuously. `src/runner/signaturePaths.ts` compiles complete routes in road-scroll units using the shared easing functions, with recorded leader paths and delayed component samples for trails. It partitions sweeps at every component turn and separates the full body sweep from actual pack-contact intervals. The spawn planner reserves those footprints through its existing path, lane-capacity and reaction-gap checks. Invalid recipes fail validation; a complete route that cannot fit is deferred or skipped, without a stationary or shortened replacement.

**Boundary:** only `src/main.ts`, `src/scenes/` and the `phaser/` folders may import Phaser or code that does, and only tests may import `src/testing/`. Every module of `src/` but the tests sits in a group of `BANDS` (`eslint.config.mjs`), the cross-game source bands with this game's rows inside them. Outside `src/testing/`, each imports only its own group and groups in lower rows, never one in its own row or above (`import-x/no-restricted-paths`, type-only imports included), so shipped code never imports Support (`src/tools/`, `src/sim/`, `src/testing/`). Each folder group that other groups import, `src/testing/` aside, has one public entry, its `index.ts`, that re-exports what they use, and a module outside the group imports only that entry (`import-x/no-restricted-paths`): the group's other modules and its stylesheets stay internal, and a nested group has an entry of its own. In `src/data/`, only `layout.ts`, `screen.ts` and `types.ts` sit behind the entry; the authored data files are imported directly. Inside a group, modules import each other directly, never through their own entry, which imports them back. An entry loads every module it re-exports, so a module that loads only in one environment (one that reads a Vite virtual module or a build define, or loads Phaser itself) sits apart from the modules that tools and tests load in Node: `src/assets/files/` holds the build's art URLs, the ramp dim sits in `src/scenes/`, and the Settings view takes the build label from its scene. `sideEffects` in `package.json` names the only modules imported for their effects alone (the stylesheets and the crash screen, `src/crash/`), so a build drops a module an entry re-exports when nothing uses it, and the bundles hold what direct imports would give them. No value imports form a cycle (`import-x/no-cycle`); type-only imports are erased, so they may, within one group. A type import is written `import type { A }`, never `import { type A }`, which still loads its module (`@typescript-eslint/no-import-type-side-effects`). ESLint enforces all of these (the game-kit repository's lint holds the kit to importing nothing from a game), so all game logic runs in unit tests without a renderer.

### Assets

- **Loading progress:** one page-lifetime DOM widget (`src/ui/dom/domLoadingBar.ts`) sits at the physical viewport's top edge, 3 CSS pixels high and spanning its full width, independent of device pixel ratio, logical fit and page-frame rotation. `src/startup.ts` mounts it once and combines module startup, the launch's one run (`launchProgress` in `src/pwa/launchProgress.ts`, shown over everything else), shared load waits and required native-resource progress. It shows nothing while idle; a measured load fills left to right, shows full for 250ms once it finishes, then fades out over 150ms and hides, under reduced motion too; work with no denominator (module loading before the launch reports, planning a walk, finding a required update's build) shows a segment a quarter of the track wide travelling left to right once every 1500ms until it finishes, then hides at once, under reduced motion too (`LOADING_TIMING` in `src/ui/progressBar.ts`, the shared timing). The launch's run is one determinate value from a first install's download through boot's reads: the kit's `LaunchProgress` counts the bytes to download and the bytes of the boot files the build manifest names, boot's loader reads fill `BOOT_READS_SHARE` of boot's part (`bootLoad` in `src/pwa/launch.ts`), and the rest fills when the first screen shows (`bootHandedOver`), so the bar never travels or restarts between the install and the first screen. A bar shows only a load the player waits for: the launch (a first install and every boot), Start walk's wait for a file still loading and its planning, Update now's switch and the forced update. Background staging of a newer build shows none. The `loadingProgress` stream (`src/loadingProgress.ts`) combines these waits: the kit's `createLayeredProgress` puts `waitedLoad`, the loads the player waits for, over `backgroundLoad`, which puts the forced update (`requiredUpdateProgress`) over Update now's switch (`acceptedUpdateProgress`). Loading uses the kit's loader rules: the game config's `loader` is `LOADER_CONFIG` (a 30s request timeout and two retries), and `BootScene`, the only scene that loads, starts the kit's `watchLoader` each time it starts, which gives every queued file that timeout, logs each file that still fails, queues it again 15s, 60s and 300s after its run (a single file, or a multi-file load such as a bitmap font or an Aseprite sheet as a whole; a missing one draws a placeholder meanwhile), and reports the runs `waitFor` marks by settled files, boot's into the launch's run and later ones to `waitedLoad`, a share that never moves back as a run queues more. - **Atlases:** a build packs every image, font PNG and sprite frame into atlas pages of at most 2048 px a side, written as lossless WebP (`src/tools/atlasPlugin.ts`, encoded by libwebp built to WebAssembly through `@andornaut/art-kit/build/webp`; `package.json` pins its codec peers `@jsquash/webp` 1.5.0 and `pngjs` 7.0.0; layout and page construction use `@andornaut/art-kit/build/atlasLayout` and `@andornaut/art-kit/build/atlasBuild`), grouped `boot`, `ui` (including fonts), `run` (including home art and choice cards) and `road`. The production art manifest includes the packed atlas index, which maps each key and frame to its page and rect. A PNG or sprite JSON the build cannot read or parse fails the build; a key with a frame too large for a page is left out with a warning and loads from its own files. `road` holds the road art drawn between depth steps: every depth step variant and the 1x of each sprite that has one, except the 1x home art (each dog, owner and walker, the tip coin and the home screen's effects, `isHomeArt` in `src/assets/atlasGroups.ts`). WebGL sets a texture's filter for the whole page, so `road` pages alone filter linearly (`smoothDepthArt` in `src/assets/phaser/manifestArt.ts`, which filters the same keys' own textures on the dev server); every other page stays nearest, and the canvas's integer zoom stays crisp, since filtering applies only inside the game's own resolution. `home`, `run` and `road` sprite frames are trimmed to their opaque pixels with their offsets recorded, so origins, flips and anchors measure the whole frame. ### Tests and simulator

- **Simulator spawn targets:** `npm run simulate -- --spawn-target 1` is the strict 100% optimisation diagnostic, requiring independently valid placement of every original configured logical request in each neighbourhood. The default target is 0.9, derived from the shared runtime delivery floor. Each neighbourhood retains its original combined active and auxiliary denominator, counting logical groups once; reports include optional omission identities and reasons and distinguish target failure, invalid geometry and missing audit coverage. A lower diagnostic target cannot relax the runtime delivery floor. Optional `SimConfig.observeSpawnPlan(observation, run)` receives successful zone observations and the actual run state after their audit metrics are recorded. Consumers may retain the supplied replay snapshot; ordinary runs retain no full plans or snapshots.
- **Planner acceptance:** `npm run planner:acceptance -- <out-dir> [--commit <sha>]` (`src/tools/plannerAcceptance/`) walks the fixed batch, six seeds on the left, straight and right routes with the expert player, and independently checks all 72 plans against the [planner contract](../docs/planner-work.md#contract): fresh audits equal to the planner's certificates and valid simulator audits, the 90% floor, 100% delivery, every attempt's candidate and propagation checks within three quarters of `SLOT_LIMITS.candidateChecks` with no reserve restart, guarantees, every positive-weight kind visible, no substitute, downgrade or capacity extra, native safety and quiet coverage, and no balanced fallback. It stops at the first failing walk, keeping that walk's observations and `failure.json`, and writes `plans.jsonl` and `summary.json` (the verdict, delivery, peak search and neighbourhood and stratum coverage) to the empty or new `<out-dir>`. Node runs it directly. It is heavy: run it in the [development container](../README.md#developing) with `--network none` and at most four CPUs, write `<out-dir>` inside the container and copy it out, and pass the checkout's commit, since the container copy has no Git metadata.
- **Simulator:** `src/sim/` plays whole runs on the real rules over a matrix of card policies, route policies, skill presets (`src/sim/skills.ts`), gear, packs and walkers. A player is a steering bot that plays the game's own walk session at its 1/60 s step: its lane moves are the steps' inputs and the policies choose each card as it opens, so a run's seed and its input log (`RunResult.inputs`) replay it in the game. The bot and the policies draw from streams of their own (`bot`, `policy`), so results are deterministic per seed. The bot reads movers by sight (`src/sim/sight.ts`), only what a player sees: a dart's cue, then its own tilt and speed once it sets off, and its turn back or stop once it happens; a rider's speed once it enters; a step once its wander mark shows, as every shape its kind may take there (a bounce's or a sway's way back once it has stepped aside, a stop-and-go's push), and an uncued step once it starts; a dive's stop once it lands and slides; a merge's way once its cue shows. Until then it reads a mover at its kind's speed, across its kind's tilt range and as standing still, and it replans its reaction time after a mover shows something new, so hits from what a mover hid measure how unpredictable it is. It reads two debuffs late, by its preset's `driftReactionSeconds`: it reacts to a Zoomies drift that long after the drift, planning until then from the lane control the pack would have without it (the walk's lane changes, pulls and steps applied to it), and it plans with the pack's lane speed before a Muddy until that long after the Muddy begins, so both cost bumps as they would a player. `--bot foresight` reads every mover's whole planned path instead, every way a stalker or shy hopper may choose its moves included, to check the planner keeps the road passable. The tuning counts are aims: each zone's plan (`Road.planned`, the quota counts from the tuning counts and weights, beside `Road.pending`, the spawns placed) is counted by walk position and zone (`src/sim/delivery.ts`), and the delivery table gives placed/planned per plan for tips, treats, lucky finds, gear drops, minor obstacles standing, darting, riding and hopping or stalking, and obstacles that open a card or not; `--delivery kinds` adds a line per kind, and `--out` writes the sums in each row's `delivery`. Each `--out` row also gives the badge counters per walk (`BadgeCounters` in `src/sim/rowSummary.ts`), judged by the achievements' own conditions on each run's facts: `meanTallies` (every lifetime tally), `meanOptionPicks` (each card option's picks, by encounter and option id), `meanBumpsByKind` (landed bumps by minor obstacle), `debuffsGot` (each debuff's `mean` and `p90` times in one walk), and the shares of walks with `cleanZoneShare` (a clean zone), `allCleanShare` (every zone clean), `lastHeartShare` (finished with an owner on their last heart) and `fullPackBonusShare` (finished with every dog of a full pack home; null for a smaller pack). Each row's `meanEarnings` and `p10` to `p90` count what walks banked, and `meanCashLost` the cash per walk lost by ending early (see Earnings). Each row's `meanSpareTreatsStored` and `meanSpareTreatsSpent` count the spare treats a walk held and gave back (`RunState.spareTreats`). Each row's `debuffCosts` gives each debuff's `meanBumpsWhile` (landed bumps while it lasted) and `meanCentsLost` (the cash it took, as the walk's changes name it: its share of each tip's pay, such as Stinky's, and the cash bumps cost while it made them cost cash, such as Spotlight's), per walk; a bump in the step a debuff starts in counts toward none. Each row's `debuffsByZone` splits a walk by zone id, per walk: `clear` gives the `meanBumps` and `meanSeconds` walked with no debuff on the pack, and `debuffs` gives each debuff's `meanBumpsWhile`, `meanPeriods` (the times the pack got it there) and `meanSeconds` (the walking time it lasted there), so a debuff's bumps per period compare against the zone's bump rate without one. The card policies (`src/sim/policies.ts`) call an option safe when it leaves no owner whose meter falls at `LOW_HEARTS` or less, and the free option the one that keeps the most money, then the most hearts, so a policy taking a free option takes a debuff option over one that costs hearts. `debuffs` takes a safe debuff option whenever one is offered, else plays as `mixed`, and `noDebuffs` plays as `mixed` among the options that give no debuff while one of them is safe, else among them all. Each row's `policyFallbackShare` is the share of cards chosen on which `debuffs` (no safe debuff option) or `noDebuffs` (no safe option that gives no debuff) fell back to play as `mixed`, and null for the other policies. Its `--help` lists the options and columns. Compare balance changes before and after at the same seed. The spawn-event table separately reports Obstacle requested, Obstacle valid and Obstacle valid/configured for minor obstacles and obstacle encounters. All-spawn totals include pickups and finds, so they use a different denominator.
- **Tests:** the game suite discovers `src/**/*.test.ts`. It covers game rules, content, assets, configuration and client adapters. game-kit and art-kit test their own implementations and public contracts in their canonical repositories; games assume those contracts and do not discover vendored or installed library tests. Adapter tests stub library calls to check the game's inputs, options and wiring. Game-specific schema validation, asset compatibility and resulting game behaviour stay in the game suite. Test helpers under `src/testing/` provide game fixtures, not another library contract suite. Scenes also have focused headless adapter tests; device playtesting belongs to the user.

## Game data

- **Card text:** generated from the effects and tuning, and exported with every card in `shared/export/game-data.json`.
- **Bump costs:** a plain bump costs its dog's owner hearts (`bumpParts` in `src/rules/run.ts`), and, while a debuff with `bumpMoney` such as Spotlight lasts and there is cash, that cash too (`bumpCash`), all of it when there is less; `bumpMoney` modifiers change it. Forgiving modifiers, such as Second chance's, forgive hearts only.
- **Choices:** `cardFor` builds a card (text, affected dogs, options disabled when unaffordable); `chooseOption` applies a choice and returns the new run state plus the outcome events the scenes animate.
- **Earnings:** the walk carries one `money` total: tips, a treat's cash, lucky finds and card options change it, and each zone's end pays every walking dog into it and records the total as `RunState.zoneEndMoney` (the starting money before any zone's end). `walkEarnings` (`src/rules/run.ts`) sets what a walk banks by how it ends (`endReasonOf`, heading home for a walk not yet ended): a finished walk banks all its money; one that ends early, heading home, interrupted and banked from its checkpoint on the next launch (one that cannot resume), or with every owner having fired you, banks `zoneEndMoney`, or all its money when card costs have left less, and loses the rest of the cash it carried (`RunResult.lostCents`). The pause menu's note says what its End walk keeps, and the Home question what it gives up: that loss plus the current zone's pay (`src/hud/homeQuestion.ts`). The end screen's breakdown counts each money change under its base cause (`earningsKind` in `src/home/endView.ts`), a treat's cash in the Tips row, and shows the loss as a Cash lost line, and the total, the best walks, lifetime earnings and the money badges all count only what was banked. The simulator banks by the same rule.
- **Effects:** card options are lists of effects from a closed set of kinds, naming money amounts and modifiers by their `tuning.ts` key. Hearts deltas are written inline, each to a target: the affected dogs, the whole pack, or the lead dog (the front affected dog in formation order). When a loss reaches several owners at once, a forgiving modifier such as Second chance's forgives the owner the loss leaves with the fewest hearts first, ties to the dog nearer the front (`takingOrder` in `src/rules/effects.ts`). A `sharedHearts` effect, the friendly neighbour's, splits its total front dog first (`shareHearts`), and a heart an owner cannot take goes to the next owner below their max, front dog first; it is lost only when every owner is full (`passHeartsOn`). Any card option may apply any debuff. A new kind is code in `src/rules/` plus a test.
- **Debuff movement:** an optional `movement` profile selects one-lane drift, an explicit `heading` or independent equal-probability `random` direction, and a `fixed` or `uniform` interval whose seconds keys name tuning values. Bounds must be positive, finite and ordered. At most one debuff may define movement because the session has one clock. The clock retains its owner, elapsed walking time and already sampled next interval in memory only; activation and each attempt sample an interval once. Every random attempt samples a fresh direction, then uses the existing safe opposite-lane or cancelled-movement fallback. Hit stops and cards freeze both the schedule and its draws. Refreshing an active effect keeps the existing schedule; expiry clears it. The seed-derived `debuffMovement-<zone>` stream is independent of cards, forks, upgrades and spawn planning. A neighbourhood boundary resets transient movement timing; neither its clock nor its RNG cursor is serialized. Restarting from a neighbourhood checkpoint reproduces its fresh schedule from the seed and zone index.
- **Format:** typed TypeScript modules in `src/data/`. Content is `as const satisfies Type`. Tuning uses plain `satisfies` so its values stay `number` for live tuning.
- **Ids:** `ids.ts` lists each table's ids as `as const` arrays, and the id types derive from the lists, not the tables; `types.ts` re-exports them. The tables are keyed by them (`satisfies Record<DogId, Dog>`, `Achievement.id`, `Zone.id`), and `src/data/ids.test.ts` fails on an id missing from either side or out of the table's order. A list keeps its table's order where that order means something (achievements, each card's options, zones) and is alphabetized otherwise, as sort-keys keeps a record table. Gameplay owns the lists and Tech their shape and the test. An id is never renamed: the save keeps them.
- **Integrity:** `src/data/data.test.ts` checks the rulebook's invariants, and type-level tests show invalid data fails to compile.
- **Live tuning:** editing a value file under the dev server updates the running game through Vite HMR. Scenes and rules read tuning at the time of use.
- **Layout:** `layout.ts` holds every authored number the screens and the walk's HUD are laid out by, grouped by screen or component, values fixed by art marked `art`. The layout modules in `src/layout/`, `src/home/`, `src/hud/`, `src/help/` and `src/ui/` derive every other position, size and room from it. `screen.ts` keeps the render resolution, the road band's rows and the road camera, and takes the walk bar's, card row's and progress line's heights from `layout.ts`.
- **Ownership:** gameplay edits values and content in the value files. Tech owns `types.ts`, `index.ts`, `layout.ts`, `screen.ts`, `src/rules/` and the tests.
- **Units:** money (integer cents), hearts, seconds, probability, pixels and multipliers are branded types (`Unit` in `@andornaut/game-kit/runtime/units`, money and hearts in `src/units.ts`), which `read` and `readTable` (`src/rules/units.ts`) give for tuning values; value files hold plain numbers.
- **Neighbourhood-only kinds:** an obstacle or minor obstacle appears in the zones that weigh it above 0 (`weightedZones` in `src/rules/zones.ts`, which the data export lists as its `zones`). Each skin of a minor obstacle with skins names its `zones`, and `src/data/data.test.ts` requires the obstacle's weight above 0 in exactly the zones its skins name.
- **Zones and forks:** `world.ts` lists the zones from easiest to hardest. A walk is `walkLength` zones from `firstZone`, ending on `lastZone`. The run's `route` lists the zones walked by id, and `zoneIndex` is a position in it. After each zone but the last, `offerFork` offers up to three unwalked zones in world order, with one path carrying no upgrade when several paths are offered. The fork before the last zone leads only to `lastZone` and carries an upgrade. Its choice is an ordinary card choice that takes any offered upgrade and appends the zone to the route.

## Save data

- **Achievements:** the game kit's `achievements` judges each badge's conditions with the registry `achievementJudge` builds (`src/save/achievementJudge.ts`), at one of three scopes: `bank`, a run as it is banked, on the save after it and the run's facts; `profile`, on launch and after a purchase, on the save alone; and `run`, one run's facts alone, which the simulator counts. Run conditions hold only with a run's facts, and conditions on what the save owns or counts across walks only with a save; only the counts across walks report progress. `src/data/index.ts` puts the catalogue in the badge wall's tier order once (`orderByTier`), so every reader takes `gameData.achievements` as it is. During a walk, the kit's `achievements/preview` says on the message strip what heading home would earn, keyed by `previewKey` and leaving out money goals and an ended walk (`previewedEarned` in `src/save/achievementPreview.ts`). The counters that span walks live in the stats: lifetime tallies of what happens on the road and of lucky finds (`dodges` counts every dog's dodge, a dodge effect's included), landed bumps by kind, every card option pick by encounter and option id (`optionPicks`, which no tally duplicates; an option's `id` in `encounters.ts` is its save key, so keep it across renames), `noFiringStreak`, the finished walks in a row with no firing: a walk with a firing resets it to 0, and a walk headed home early with no firing leaves it unchanged, and `runs`, the walks by how they ended: `walksPlayed` counts every one, and `walksFinished` only `runs.finished`, the walks that finished every zone from the first. A run keeps its own share of the tallies, bumps and picks in its counters, checkpoint included, until it is banked.
- **Contents:** bank, owned dogs, gear, slots and walkers, chosen walker, last loadout, stats and logbook, shown hints, whether the help has been seen and the checkpoint (with the run's route and its resume point), all referenced by data ids.
- **Earned badges:** kept apart from the save, in the kit's earned record (`earnedFormat`, version `EARNED_VERSION` in `src/save/storage.ts`, which a format change bumps under the compatibility policy below; the current pre-1.0 format resets older records) under `archies-dog-walks.achievements`: the ids earned, in the order earned, and those not yet celebrated, with no time. Loading drops ids the data no longer has; a record that fails to load is kept under `archies-dog-walks.achievements-backup`. A badge earned on launch or by a purchase waits to be celebrated on the home screen, and counts as celebrated once the celebration takes it; a run's badges are celebrated on the end screen as it is banked. A badge earned and not yet celebrated when the page closes is celebrated on the next launch. The Cheats modal's Reset save clears the record too.
- **Derived values:** the save holds nothing a load can rebuild from the rest of it or the game data, and nothing the game never reads. The total times fired is each dog's added up, and the best walk's earnings are the largest best by pack size (`src/save/stats.ts`). `owned` leaves out the starting dog slots and the free dogs and walkers, which every load adds back (`storedSave` in `src/save/schema.ts`). The last walk's firings are dog ids. A checkpoint's dogs keep only the zone each owner fired you in, and it keeps no count of owners on their last heart, which only a finished walk uses. Lifetime bumps by kind and option picks count every kind and option, not only those a badge reads.
- **Device settings:** the FPS counter, music and effects volumes, mute and reduced motion are kept apart from the save, each in `localStorage` under its own key (`SETTINGS_KEYS` in `src/save/settings.ts`: `archies-dog-walks.fps-counter`, `.music-volume`, `.muted`, `.reduced-motion` and `.sfx-volume`; a switch as `on` or `off`, a volume as its number from 0 to 1), so a save reset leaves them. A setting with nothing stored, or a value that does not decode, takes its default, and reduced motion follows `prefers-reduced-motion` until the player sets it. A change is applied at once and writes only the settings it changed (`DeviceSettings`); where the browser refuses storage, it lasts until the page reloads. `src/scenes/sceneSettings.ts` keeps the page's settings in the game's registry for every scene.
- **Format:** one JSON document under `archies-dog-walks.save` with a `version` field; every write replaces it. A save under an earlier key is never read.
- **Resume:** a walk closed without heading home resumes on the next launch at the start of the neighbourhood it was in, or at the fork it waited at, opening straight into the walk under the pause menu. The checkpoint's `resume` is the session at that point (`ResumeWalk` in `src/save/resume.ts`): the run state whole (pack and hearts, walker, gear, money, debuffs, modifiers and immunities, route and zone index, counters), the road as the last zone left it (lane, items still on it, the path's last row), pulls and clocks, and the seed with how many numbers `cards`, `forks` and `upgrades` have drawn, which `runStreams` draws again; each zone's plan is drawn again from its own seed-named streams, so the resumed walk plays as the walk itself would have from there (`src/sim/resume.test.ts`). It is stored as text in its own versioned format (`RESUME_VERSION`, the kit's `versionedSave`, no migrations) and checked against the game's content on launch (`launchWalk`): a dog, zone, gear, upgrade, debuff, encounter or tuning key the game no longer has, another version, or a point that is not the checkpoint's own walk banks the run as heading home and opens home, keeping text that could not be read under `archies-dog-walks.resume-backup`; the rest of the save loads as it is. A dev link that names a run banks it rather than resuming it, as its own walk starts. The resumed walk counts once: the launch banks nothing for it, and the walk banks as it ends (finished, headed home or every owner firing you), with the counters and money it carried from its start, clearing the checkpoint; the zone it replays counts only as replayed. Taking the walk drops its resume point from the stored checkpoint until the walk saves again, so a resumed walk that crashes before then banks on the following launch.
- **Scenes:** `src/scenes/profileStore.ts` holds the loaded save for every scene and is the only way scenes read or change it.
- **Scope:** one profile per browser, local only, per origin.
- **Storage:** the game kit's save store (`@andornaut/game-kit/runtime/save/*`) on an async interface, with the game's keys and its format (`gameSaveStore` in `src/save/storage.ts`, `saveFormat` in `src/save/load.ts`), and the kit's earned store beside it (`gameEarnedStore`), which applies its writes in call order. The web adapter wraps `localStorage`. When storage fails, the game stays playable and says progress won't be saved.
- **Validation:** a Valibot schema parses every load. Unknown ids are dropped. A save that fails validation is kept under `archies-dog-walks.save-backup` and the game starts fresh.
- **Version:** compatibility follows the game's runtime release version under the shared [Saves and cheats policy](https://github.com/andornaut/game-coordinator/blob/main/docs/game-policies.md#saves-and-cheats), not the save schema's age or a first-release declaration. In the current pre-1.0 game, a save-format change or an id rename (a dog, gear item, walker or encounter) bumps `SAVE_VERSION` (`src/save/schema.ts`) and an older save resets to a default save, kept as a backup like one that fails validation; there are no migrations. An added optional field, which an older save loads without and an older build ignores, needs no bump (the checkpoint's `resume`); any other format change does. A save from a later version than the running game (after a rollback, or on a stale page) is left as stored: the game plays from a default save in memory, writes nothing for the session, and requires the newer version (the forced update, below). An earned record from a later version does the same, the save in memory being the stored one.
- **Writes:** on a purchase, a loadout, walker or hint change, the help's first close, at each fork, as each zone after the first starts and as the tab hides mid-walk (the checkpoint, with its resume point), and at run end. An unfinished run resumes on the next launch, or, when it cannot (Resume), is banked as a run that headed home. `ProfileSession` (`src/save/profile.ts`) writes the save and the earned record one after another in the order made: a banked run's badges before the save that banks it, since its facts are gone once it is banked, and a purchase's save before its badges, which the next launch awards again if they were not written.

## Phone

- **Audio:** resumes from iOS's `interrupted` or `suspended` state on each return to the foreground and each gesture (`touchend` on iOS), unless the settings mute it.
- **Back:** `guardBackNavigation` (the kit’s `web/pwa/dom/backNavigation`, its history entry marked `archiesDogWalksBackGuard`, each back it keeps sending `PHONE_EVENTS.backPressed`) catches back two ways, in every browser tab and in an installed app whose window a script can close, and in no other installed app (`leaveOffered` in `src/pwa/index.ts`, read at load from the kit’s `appCannotClose`). Leaving is offered only in such an installed app (`exitShown`, from the kit's `canExitApp`), since leaving a browser tab would navigate away rather than close. The HTML spec lets a script close only a window whose history holds a single entry, and of installed apps only Chrome's Android app and Chrome's and Edge's desktop app windows honour it (the kit's `APP_WINDOW_CLOSES`); iOS's and iPadOS's Home Screen apps and Firefox for Android's app never close, and Samsung Internet's and Edge's Android apps and macOS Safari's Dock apps are taken not to. An app that would need the guard entry (no close watcher) or was launched with pages before the game cannot close either. In those apps `setupPhoneApp` leaves back to the browser: no close watcher and no guard entry. Wherever leaving is not offered, a browser tab included, there is no Quit?, the home top bar has no Exit and Q does nothing. Where the browser has `CloseWatcher` (Chrome 120 and later, Firefox 149 and later), a close watcher, created at load and again after each `close` it fires, takes the Android back gesture or button; it adds no history entry, so a launch with nothing before the game keeps one entry, which lets `window.close()` close the window. A close caused by an Escape keydown is not a back press, since the game's own keys handle Escape. Firefox for Android hands back to a close watcher only when its history can go back, and otherwise leaves the page, so `backCloseWatcher` uses none in a Firefox for Android tab. Where there is no close watcher, or the history already holds more than one entry (a page before the game), a guard history entry takes back by being popped, pushed again on each pop; it also catches a desktop browser's Back button, which is not a close request. The user's back skips an entry with no user interaction recorded on it (Firefox) or one that added an entry without user activation (Chrome), and with nothing before it is the browser's own. So the guard is pushed only from input the browser records before the page sees it (`BACK_GUARD_GESTURES`: a keydown other than Escape, or a pointerup; a touch's pointerdown is recorded on no entry), never at load, and back before the player's first input leaves the game. Each back, in a tab or installed, dispatches `PHONE_EVENTS.backPressed`, which the running scene on top takes (`onBackPressed`): an overlay closes (`listenDismiss`), the walk acts as `walkBackAction` (`src/hud/topBar.ts`) says (the Home question, which only the fork card's End walk asks, closes back to the fork card), the end screen goes home, and the start screen closes its detail card or, with none, opens `QuitScene` where leaving is offered and otherwise does nothing (`homeBackAction`). Quit? is drawn by `addQuestionPanel` (`src/scenes/questionPanel.ts`), as the pause menu and the Home question are, and its Quit leaves as the home top bar's Exit does (`exitGame`, the kit’s `exitApp`): the installed app's window closes (`window.close()`). Leaving never navigates to another page.
- **Install offer:** `/` and `/play/` both link the manifest, whose `scope` is `/` and `start_url` `/play/`, so an install from either opens the game. `watchInstall` (the kit’s `web/pwa/dom/installFlow`) holds Chromium's `beforeinstallprompt`, its default prevented so the browser shows no banner of its own, and follows `appinstalled` and the display mode; `installState` (the kit’s `web/pwa/installState`) reports `installed`, `prompt` or `steps`, and `steps` is any browser holding no prompt. `stepsKind` is the `InstallStepsKind` the kit's `installStepsKind` finds from the user agent: `chromiumAndroid`, `chromiumDesktop`, `firefoxAndroid`, `firefoxDesktop`, `ios` (any iOS browser, or an iPad asking for the desktop site), `other` (unlisted browsers, Opera and WebViews), `safariMac` or `samsungInternet`. Firefox opens the installed page in `standalone` display mode, so the display-mode query finds it installed. Until it is `installed`, Settings has an Install row (its sole action an Install button centred in the row, its icon and label one ink group, `ICON_LABEL_GAP` apart) and the home page an Install button beside Play (`src/homePage/main.ts`, on the kit's `wireInstallButton`, its words in `pages/index.html`). A tap calls the held prompt's `prompt()` before any `await`, while the tap still counts as a gesture; a prompt shows once, so after the player's choice the tap shows the steps until the browser hands over a new prompt on a later visit. Where the outcome is `steps`, the tap opens that kind's steps (`menuText.settings.installSteps.<kind>`, typed `Record<InstallStepsKind, ...>` so every kind has them): a card over Settings, led by the glyph of the button the steps start from (`icon-share` on iOS, `icon-browser-menu` in Chrome and Firefox for Android, none for the other kinds, each left out while missing), and a `<dialog>` on the home page, which shows the `data-steps` section of `pages/index.html` for the kind, its words checked against the data, and whose first button closes it.
- **Install suggestion:** after the first finished walk, the walker's bubble on the start screen says `homeText.bubble.install` once per device, in place of the how-to or welcome back, while the game offers installing (`walkerLineKey`), except in Firefox on a desktop (`firefoxDesktop`), which cannot install it. The flag `archies-dog-walks.install-nudged` (`src/pwa/installNudge.ts`) sits in the save's storage under its own key, not in the save, since installing is per device; while it is unread or unreadable the suggestion counts as shown.
- **Installable web app:** `/manifest.webmanifest` and a router service worker, `/sw.js`, the kit’s `web/pwa/dom/serviceWorker` run with the game's `CACHE_POLICY` (`src/pwa/cachePolicy.ts`, `src/pwa/serviceWorker.ts`), built by the kit's precache plugin (`src/tools/pwa/precachePlugin.ts`). The router downloads nothing: it serves each window the build it is pinned to, or the active one, and leaves the page installer's `no-store` requests to the network. The build also writes the build manifest, `/.game-kit/manifest-<version>.json` (every file the complete build needs offline, the page, its build output, the public files it links, the web manifest's icons and the hashed art with both formats of every sound, each with its SHA-256 and size, and the boot files, `bootFiles` in `src/tools/pwa/precacheArt.ts`), the pointer `/.game-kit/build.json`, which names the deployed version and its group archives, and one gzip-compressed archive per update group, `/.game-kit/group-<sha256>.bin` (the pointer gives each archive's decoded size and SHA-256 and its encoded size; a device decodes it with `DecompressionStream`, which every browser the build's Vite target names has, and verifies it before storing it). The build also writes each archive decoded at `/.game-kit/archive-<sha256>-0.bin`, the only form an installed build on game-kit 0.72.0 or earlier can stage. `updateGroup` in `src/tools/pwa/assetGroups.ts` names each file's group (the page, the icons, Phaser, the other code, the page fonts, the art manifest, each atlas, the DOM sheets, the art fonts, the sound effects and each music track), and the kit splits each group's sounds into one archive per format, so a device installs only the archives without a format and those of the format it plays. The files only the installed game requests (`gameOnlyFiles`: the code only the game's dynamic import reaches, and the art under `/assets/art/` no built page or stylesheet names) ship only inside the archives; every page, its static imports, the public files it links and the site's art (the nav bar's and home page's DOM sheet images) stay files as well, for a first visit and the site; `_headers` serves the pointer `no-store` and each manifest immutable (`FILE_RULES` in `src/headers/securityPolicy.ts`). `public/manifest.webmanifest` is a template whose description `webManifestPlugin` (`src/tools/pwa/webManifestPlugin.ts`) fills from `menuText.settings.installDescription`, on the dev server and in the build. Both pages set the same theme colour, the palette's ink, and the mobile and Apple web-app meta. A build writes each icon (`HASHED_ICONS` in `src/tools/pwa/icons.ts`: the manifest's, and the pages' favicons and apple-touch-icon) under a content-hashed name in `/assets/` and points the built pages and `/manifest.webmanifest` there (the kit's `hashedIconsPlugin`), so a redrawn icon reaches an installed app with the version that names it; the manifest keeps its name. A public file the page links, or an icon the manifest names, that is missing fails the build. The host must serve the built bytes unchanged (no HTML injection, beacons, email obfuscation or image recompression), since the installer verifies every file against the manifest. The launch is the kit's one loader (`createLaunch` in `web/pwa/dom/launch`), started by `startLaunch` (`src/pwa/launch.ts`) from `src/startup.ts` before the game's modules load, in the production build only. Nothing reads or writes a save or constructs Phaser until its `run()` resolves `play` (`launchGame`); `reloading` means another document takes over. A first visit, with no active build, registers the router and installs the complete build in the foreground under the loading bar: it reads the pointer once, downloads the device's archives one at a time and stores each only once its size and SHA-256 match, checks their files against the manifest, and then records the build active and plays it from the installed build, offline from then on. Only then do the game's modules, art and sounds load, from the installed build. A first install that fails on the network or verification shows Loading failed with Retry before the game exists (`mountLaunchFailure` in `src/ui/dom/launchFailure.ts`, the kit's hardened failure view in the loading error's look), and each Retry press resumes the install once. Where the device cannot install, the router failing to register (`unsupported`) or storage being full (`quota`), the kit calls `onNetworkPlay` and the game plays from the network for that session, the walker's bubble saying why after its other notices (`networkPlayReason`, `networkPlayNotice` in `src/home/homeLines.ts`: `homeText.noticeOnlineUnsupported` or `homeText.noticeOnlineQuota`); the next launch tries the install again. A production browser without Service Worker or Cache Storage support shows the shared unsupported-browser screen before the game or installer starts. A later launch plays the active build at once, then reads the pointer, on launch, entry to play, genuine return to Start and foreground return (the shared updater coalesces overlapping wake signals): a newer build stages in the background, fetching only the archives whose hash changed and copying the rest from the installed build, and never shows Loading failed or interrupts play; a failed staging is retried at the next check. A staged build that finishes during a session raises the Update now prompt once (`onUpdateReady`, `PHONE_EVENTS.updateReady`) over whatever screen shows once boot has handed over (`UpdateScene` and `watchUpdateOffer` in `src/scenes/UpdateScene.ts`): the update modal (`homeText.update`, `updateModalLayout` in `src/home/homeLayout.ts`) over the dimmed screen in the region under the top bar. It holds play still: every running scene pauses as under any overlay, and a walk pauses under its pause menu (`holdForUpdate` in `src/scenes/RunScene.ts`), back being the prompt's while it shows. Update now (`acceptUpdate`) closes the card, shows the travelling bar, waits for the save (the walk's checkpoint, `checkpointForUpdate`, then every pending profile write, `profileWritesSettled`), then activates the staged build and reloads into it with no download; a failed switch shows the card again titled `homeText.update.failure`. Cancel, the close control, a tap outside, back, P and Escape dismiss it (`dismissUpdate`): play continues on this build, the prompt does not return this session unless a newer build stages, and the next launch applies the update silently, the router promoting the staged build at that launch's navigation before any game code or save access. Start walk stays closed while Update now switches (`updateAccepting`). The home page registers the router too (`registerRouter` in `src/homePage/main.ts`), installing nothing, so an app installed from `/` opens through it. A save or earned record from a newer version forces the update: `BootScene` calls `noteSaveStorage` once the profile opens, which calls the launch's `requireNewer`, and the kit then stages and switches by itself and never offers it. `requiredUpdate` follows the kit's `onRequireNewer` (`PHONE_EVENTS.requiredUpdate` on each change). While one is required the save stays as stored, no walk starts (a resume or a dev walk link opens home instead) and Start walk stays closed (`startOpen`). On `"updating"`, `requiredUpdateProgress` (`src/pwa/requiredUpdate.ts`) feeds the shared stream in `src/loadingProgress.ts`, filled by the newer build's staging, and the page switches to it as soon as it is stored and verified. On `"unavailable"` (offline, no newer version on the server, a failed staging, or no launch) the walker's bubble says `homeText.noticeUpdateNeeded` first (`requiredNotice`), and the kit tries again on the window's `online` event and whenever the page comes back into view.
- **Installed app:** the game page has no site nav bar (`/play/` loads neither `public/nav.js` nor `public/nav.css`), and nothing on it goes to another page: Update now, the crash screen and Reset save reload `/play/` or load it with other parameters, and leaving (Exit, Quit) only closes the installed app's window (the kit’s `exitApp`). The game tests once, on first use, whether it runs in an installed app's window (`browserToolsOn` in `src/cheats/browserTools.ts`, from the kit's `runsInAppWindow`: `fullscreen`, `standalone` or `minimal-ui` display mode, which Firefox for Android's app may report, or iOS's `navigator.standalone`), and uses that result to gate browser-only URL tools. Installed apps ignore URL run setup, replay logs and `dev=1`. Cheats is available through one entry in the applicable Menu or Pause.
- **Persistent storage:** at boot of the installed app (`installState` reads `installed`), `requestPersistentStorage` (the kit’s `web/pwa/storagePersistence`) asks `navigator.storage.persist()` once to keep the site's storage, the save included, from eviction under storage pressure or after Safari's 7 days without a visit, unless `persisted()` says it is kept already. A browser tab never asks, so Firefox never prompts the player; it only reads `persisted()`. Boot never waits for it, and a missing API, a refusal or an error leaves storage as it was.
- **Phone events** (`PHONE_EVENTS` in `src/pwa/events.ts`): going back (in a browser tab) and hiding the app each open the pause menu, as do a window `blur` and a change of the page frame's turn (`onFrameTurnChange`, `RunScene`); hiding also writes the checkpoint. The run holds a screen wake lock.
- **Portrait only:** the manifest and `lockGameOrientation` ask for `portrait`, which only an installed app on some platforms grants. Elsewhere a touch screen in landscape (a phone or tablet on its side, `turnedFrameQuery("portrait")`) turns the page frame onto its side, so the game stays upright for the device: the kit’s `web/view/frameTurnPortraitGame.css`, imported first by `src/main.ts`, turns `body` by -90 degrees, or 90 on the screen's secondary landscape (`watchFrameTurn`, in `setupPhoneApp`), and gives the turned frame's own safe-area insets as `--inset-*`, which the page's CSS uses in place of `env(safe-area-inset-*)`. Phaser measures `#game` and reads pointers through the turn (`followFrameTurn` in `src/main.ts`, given `pageFrameWatch()`), and refits until the sizes settle whenever `#game`, the visible area or the turn may have changed, a return from the background included, with a check four times a second while the page shows; the page is no taller than the visible area (`--page-height`). The page's CSS places the canvas in the turned frame, and `pagePresses` maps a press on the page through the turn (`pageFrameTurn`). A mouse's window never turns.
- **Security headers:** the parent security headers plugin, given the game's policy (`src/headers/securityPolicy.ts`) by `src/tools/headers/securityHeadersPlugin.ts`, writes `dist/_headers` at build time: nosniff, referrer and permissions policies, and a CSP per path allowing `'self'` plus hashes of each page's inline blocks. No script adds a style element or attribute, so no hash depends on a script's text, and only the CSSOM (`element.style`) styles an element: the build fails for a style element or attribute that a built script adds or a built page's markup carries, or a constructed stylesheet a script adopts (`inlineStyleCheckPlugin` in `src/tools/headers/inlineStyleCheckPlugin.ts`, `src/tools/headers/inlineStyle.ts`), less Phaser's, which the game never reaches, each allowed by name (`PHASER_INLINE_STYLES`), and `src/tools/headers/inlineStyle.test.ts` checks the sources the same way. Content-hashed output under `/assets/*`, the hashed art and icons included, is cached immutably, and the build fails for an unhashed name there. Font descriptors (`*.fnt`) are served as `text/xml`, which Cloudflare compresses.
- **Sound format:** each sound ships as Ogg and AAC (`.m4a`). The page picks the first the browser plays (`browserSoundFormat` in `src/audio/dom/index.ts`), boot loads only that file, and the launch passes it as `createLaunch`'s `soundFormat`, so the install fetches, counts and checks only that alternative of each sound, matched by its URL extension (`.ogg` or `.m4a`).
- **Touch:** the canvas takes no browser gestures (`touch-action: none`). A tap's `fx-tap` burst plays in its own scene over every other but the dev overlay (`TapBurstScene`), started with the game and never paused or stopped, so it plays out over whatever the tapped scene does next. A page, overlay, card or confirm that a tap opens opens at once, the burst playing on over it. A button that dips (`FEEDBACK.pressDipMs`) acts once its dip has played, except one that opens a page or card, which acts as the finger lifts, its dip playing on under what it opened (`opens` in `src/input/targetPress.ts`, `afterMsUnderOverlay` in `src/scenes/overlayClock.ts`). A card or confirm drawn in its own scene opens as the tap acts; an overlay scene, and a top-bar page, opens at Phaser's next step, which applies queued scene operations, so a second open asked of the same scene before then is dropped (`openGuard` in `src/input/openGuard.ts`, which `openOverlay` and `openHomePage` go through). Full-screen pages retain their scene-owned navigation. The top modal also owns taps in all letterbox bars. A dismissible modal closes one layer without passing that tap to the restored view. A mandatory card consumes the tap and stays open. Ordinary modal overlays, including update notices, place their corner close control through `src/ui/closeControl.ts`, following the [Art modal geometry](../art/layout.md#modals). Every modal card with a title has one layout (the native adapters in `src/scenes/questionPanel.ts`: the detail cards on the home screen, in the Pet shop and on the walk, the install steps and Settings): the card's own background with no title bar, its plum title on the title row across the card's top (`cardTitleRow`), and the close control at the panel's top right. The pause menu, the Home question, Quit? and the badge celebration keep their own panels with the same title placement and close control (`cardTitleRow` in `src/ui/modal/titleRow.ts`); the badge celebration's badges sit low enough to clear the control (`stripUnderClose`). Every modal card's close control does what a tap outside it does: resume, keep walking, keep playing, cancel or close. Modal title ink centres across the whole panel, with the [Art title clearance](../art/layout.md#modals) reserved symmetrically on both sides (`src/ui/barTitle.ts`). Long titles wrap at full font size; install-step panels grow their header and body offset by each extra title line. A card with no close control reserves only its normal padding. Bespoke page headers keep their separate close clearance.

## Dev tools

In a browser tab, `/play/` reads a run setup from the URL; invalid values, unknown ids included, are warned about and ignored. A URL with any run parameter (all but `dev` and `route`) skips the home screen and starts the walk, its pack and gear replacing the saved loadout for that walk only. Such a walk saves, banks and earns badges like any walk. Reaching the home screen removes every parameter in the table but `dev` from the URL, leaving any other.

| Param        | Value                                                             | Default        |
| ------------ | ----------------------------------------------------------------- | -------------- |
| `dev`        | `1` shows crash details and sets the `archiesDogWalksGame` global | `0`            |
| `gear`       | a gear id, or `none`                                              | saved loadout  |
| `invincible` | `1` turns on Invincible owners                                    | `0`            |
| `money`      | whole cents                                                       | starting purse |
| `pack`       | 1 to 3 dog ids, comma-separated                                   | saved loadout  |
| `route`      | zone ids walked, from the first                                   | pre-fork route |
| `seed`       | integer 0 to 4294967295                                           | random         |
| `speed`      | scroll-speed multiplier                                           | 1              |
| `walker`     | a walker id                                                       | saved walker   |
| `zone`       | 1 to the walk's length                                            | 1              |

- **Build label:** the crash screen's dev details and the foot of Settings show `v<version> · <commit>` (`BUILD_LABEL` in `src/buildLabel.ts`, through the kit's `buildLabel`), from `__APP_VERSION__` (package.json) and `__COMMIT__`, which `vite.config.ts` defines from `WORKERS_CI_COMMIT_SHA`, else `git rev-parse HEAD`, else `dev` (the kit's `shortCommit` in `web/build/buildVersion`).
- **Cheats:** browser tabs and installed apps offer one Cheats entry directly in the applicable Menu or Pause. It opens the Cheats page over its invoking menu (`CheatsScene`, with `src/scenes/cheatsPage.ts`, drawn by `src/hud/dom/cheats.ts` from `cheatsView` in `src/cheats/cheatsView.ts`). Its rows follow `docs/design/gameplay/cheats.md`, with actions disabled where they do not apply. Each button row is a Game Kit action group (`createActionGroup`) arranged on the art-pixel grid (`project` and `origin`), a pair side by side and a sole button centred, each press area its face. Back, Escape and the system back close Reset save? first, then return to the invoking menu and restore focus to its Cheats entry. The cheats are pure changes in `src/cheats/cheats.ts`, and act on the real save as normal play does: a walk played with cheats on saves its checkpoints, banks and earns badges. The grants (Unlocks, and Money, which adds to the bank) go through `updateProfile` like any change, so they are written at once, and redraw the Start screen (`CHEATS_CHANGED_EVENT`). A live edit of a walk (Invincible owners, Start at) stops its replay recording (`RunRecorder.abandon`). Next walk choices wait in the game's registry (`src/scenes/cheatChoices.ts`) for the next Start walk, whose setup (`nextWalkSetup`) and invincible-owner cheat they set; every walk notes it started (`noteWalkStarted`), and the Start screen that follows clears them (`clearNextWalkAfterWalk`). Movement speed is available through browser-tab run links and test setup. Reset save (`resetSave`) writes a new player's save and clears badges after every earlier write, and prevents later writes until the Start screen reloads.
- **FPS counter:** the `fpsCounter` device setting (`archies-dog-walks.fps-counter`, Off by default) shows `game.loop.actualFps` as a whole number about four times a second, fixed at the frame's bottom-right corner inside the safe area and over everything (`src/ui/dom/fpsCounter.ts`), in a browser tab or an installed app. Its switch is the last Settings row, below Install when shown.
- **Input log:** lane moves, card choices and heading home are recorded with their step's time in a versioned log (a replay rejects a log of any other version), whose setup names the pack, gear, walker, route and Invincible owners, so a replay does not depend on the saved loadout or the Next walk choices. RunScene writes the finished run's log to `sessionStorage` key `archies-dog-walks.dev-last-log` and the next walk started plays a log found under `archies-dog-walks.dev-replay`. A replay writes nothing to the save: no checkpoint and no banked run, and it ends on the home screen. A resumed walk records no log, since a log replays a walk from its setup.
- **Random streams:** one seed feeds `ambient`, `cards`, `debuffMovement-<zone>`, `distractions`, `forks`, `quips`, `upgrades` and the planner's streams, where `<zone>` is the position in the walk. The planner draws each purpose from a stream of its own, so a draw added for one never shifts another (`src/runner/slotEntropy.ts`). A zone's requests outside the slot search draw from `zone-<zone>-<purpose>`: `gearDrops`, `luckyFinds` (each kind's count), `luckyHops` and `luckySteps` (a moving find's hops and steps), `luckyMovement` (whether each find moves), `luckyOrder` (the finds' shuffle) and `skins`. The slot search draws its path from `slots-<zone>-path`, each slot's kind order and layout from `slots-<zone>-<slot>-source-order` and `slots-<zone>-<slot>-layout`, and the mover of each kind in each slot from `slots-<zone>-<slot>-<kind>-<purpose>`: `draws` (the fixed draws of `drawMover`, `src/runner/moverDraws.ts`), `hops` (a hopper's ways to hop) and `steps` (a stepper's steps). The planner's streams restart from the seed with no saved count. `cards` draws a dog's dodges (a dog with no dodge chance draws nothing), `forks` draws its paths, `upgrades` draws their upgrades and `debuffMovement-<zone>` draws movement intervals and directions. `cards`, `forks` and `upgrades` count their draws, which a resume point keeps; a resumed walk's `ambient`, `distractions` and `quips`, which only the views draw, start again from the seed.
